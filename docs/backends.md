# backends.md — سه سرویس کوچکی که خودت مستقر می‌کنی

همه روی همان VPS موجود (`194.56.148.100`، nginx + pm2) قابل اجراست. هیچ‌کدام به دیتابیس سنگین
نیاز ندارند: لایسنس → SQLite/Postgres کوچک، آپدیت → فایل استاتیک، تیکت → همان دیتابیس.

## ۱) سرور لایسنس — `licenses.gympro.ir`

| متد | مسیر | ورودی | خروجی | نکته |
|---|---|---|---|---|
| POST | `/v1/activate` | `{licenseKey, machineId, appVersion}` | `{license, signature}` | هر فعال‌سازی یک اسلات مصرف می‌کند؛ اگر `activationsUsed >= maxActivations` → 409 |
| POST | `/v1/deactivate` | `{licenseKey, machineId}` | `{ok}` | اسلات آزاد می‌شود (انتقال دستگاه) |
| POST | `/v1/heartbeat` | `{licenseKey, machineId, appVersion, updateEntitlementUntil}` | `{serverTime, revoked?}` | فقط برای تشخیص ابطال/انتقال؛ **نبودِ اینترنت هرگز قفل نمی‌کند** |
| GET | `/v1/pubkey` | — | `{key, alg:'Ed25519'}` | برای verify در ابزار پشتیبانی |

قواعد:
- کلید خصوصی **فقط** روی سرور و در فایل با مود `600`؛ هیچ‌وقت در بیلد نیست. کلید عمومی داخل برنامه hardcode است.
- هر پاسخ `activate` یک `license.json` کامل می‌سازد و امضا می‌کند؛ کلاینت مستقلاً verify می‌کند.
- نگه‌داری داده: `licenseKey, machineId, email خریدار, تاریخ‌ها` — نه بیشتر. `machineId` هش است،
  پس «شناسهٔ سخت‌افزار خام» ذخیره نمی‌شود.
- Rate limit روی IP + روی `licenseKey` (۵ خطا در ۱۵ دقیقه → ۴۲۹).
- لاگ دسترسی ۹۰ روز، سپس حذف.

## ۲) سرور آپدیت — `updates.gympro.ir` (فایل استاتیک)

```
/latest.json                      ← مانیفست کانال stable
/latest-beta.json
/releases/GymPro-Setup-1.4.2.exe
/releases/GymPro-Setup-1.4.2.exe.ed25519   ← امضای جدا (hex)
```
`latest.json` = `{ version, minSupported, mandatory:bool, notes:[{fa:'…'}], sha256, size, publishedAt }`.
کلاینت: دانلود → `sha256` تطابق → `verify(signature, sha256+version)` → نصب.
`mandatory:true` برای نسخه‌های بحرانی (مثلاً تغییر اسکیمای داده) → آپدیت اجباری تا نصب.
`minSupported` برای جلوگیری از ارتقای پرشی از نسخهٔ خیلی قدیم (پیام «ابتدا ۱.۲.۰ را نصب کن»).

نکتهٔ مهم: `electron-updater` مانیفست خودش (`latest.yml`) را می‌خواهد؛ طرح بالا **جایگزین** آن است
و نصب را ما مدیریت می‌کنیم تا امضای Ed25519 اجباری باشد. اگر بخواهی از `electron-updater` بدون
دست‌کاری استفاده کنی، امضا به `sha512` محدود می‌شود که شرط «امضای Ed25519 قبل از نصب» را
برآورده نمی‌کند — این تصمیم را آگاهانه در فاز ۹ می‌گیریم.

## ۳) API پشتیبانی — `support.gympro.ir`

| متد | مسیر | کار |
|---|---|---|
| POST | `/v1/tickets` | ایجاد تیکت؛ خروجی `{remoteId, ticketNo}` |
| POST | `/v1/tickets/:id/messages` | پیام جدید + پیوست‌ها (`multipart`) |
| GET | `/v1/tickets?since=<iso>` | تیکت‌های تغییر‌یافته برای همان دستگاه (با توکن دستگاه) |
| GET | `/v1/tickets/:id` | تاریخچه + پیام‌های جدید |

- احراز هویت: `deviceToken` (تصادفی ۳۲ بایتی، در `/data/.device`) + `licenseKey`؛ هیچ رمز کاربری.
- عضویت/موبایل عضو **هرگز** نباید در تیکت ارسال شود؛ ما در UI هشدار می‌دهیم و در سرور فیلدهای
  مشکوک را نمی‌پذیریم (اعتبارسنجی طول/فرمت + هشدار).
- سقف پیوست ۵MB، فقط png/jpg/webp/pdf/txt/log، پسوند اجرایی رد می‌شود.
- نگه‌داری: تیکت بسته‌شده ۱۸ ماه، سپس حذف خودکار؛ **این را در `privacy-policy` نوشته‌ایم**.
- Poller در کلاینت هر ۶۰ ثانیه، با backoff نمایی هنگام خطا (۶۰s → ۱۲۰s → … → سقف ۱۵m) تا
  به سرور خودت حملهٔ ناخواسته نشود.

## هزینهٔ عملیاتی (تخمین، برای برنامه‌ریزی)

هر سه سرویس روی یک VPS ۲GB با pm2 و nginx: بدون هزینهٔ اضافه. پهنای باند فقط برای آپدیت
(هر بیلد ~۹۰MB) — با ۱۰۰ نصب، هر انتشار ~۹GB. اگر رشد کرد، آپدیت را به CDN/آروان منتقل کن.
